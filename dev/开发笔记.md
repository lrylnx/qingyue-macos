# 轻阅 开发笔记

记踩过的坑和当时的判断依据，方便下次不重犯。功能说明见 `../README.md`。

## 构建

**必须用 Xcode 自带的 SDK，不能用 `xcrun --show-sdk-path` 的结果。**
本机 `xcrun --show-sdk-path` 指向 CommandLineTools 的 SDK，比 Xcode 自带的新；里面的 `.swiftinterface`
用了 Swift 6.4 的语法（对 `Swift::Comparable` 这类写法），Xcode 16 带的 Swift 6.0 读它直接报一堆
`expected declaration`。所以 `build.sh` 里硬编码：

```
/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX.sdk
```

**没装 Xcode（只剩 CommandLineTools）时，不能用最新的 SDK。** 从 macOS 26 的 SDK 起，
SwiftUI 的 `@State` 已经改成宏实现，而宏插件 `libSwiftUIMacros.dylib` 只随 Xcode 下发，
CLT 里没有（`/Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/` 只有
ObservationMacros / SwiftMacros / TestingMacros）。报错长这样：

```
error: external macro implementation type 'SwiftUIMacros.StateMacro' could not be found for macro 'State()'
error: cannot find '$dropTargeted' in scope      ← 真正原因被这行淹掉
```

后面那句 `cannot find '$xxx' in scope` 很容易让人以为是自己代码写错了（`@State` 属性明明就在那儿）。
`build.sh` 现在按这个顺序挑 SDK：`$SDK` 环境变量 → Xcode 自带 SDK → CLT 里 <26 的最高版本
（那代 `@State` 还是普通 property wrapper）。实测 `MacOSX15.2.sdk` + Swift 6.4 编译器能正常编出
macOS 14+ 的产物。

**C 桥接要按架构各编一份。** 只编一份 arm64 的 `zipshim.o` 去链接 x86_64 时，ld 只给一句
`found architecture 'arm64', required 'x86_64'` 的 warning，接着 `_lr_inflate` / `_lr_deflate` / `_lr_crc32`
全成 undefined symbols。所以循环里按 `$arch` 各编一份 `zipshim_${arch}.o`。

**CLI 必须跟 App 一起重编。** 踩过一次：改了 `HTMLShell.swift` 里的 CSS，只跑了 `build.sh`（那时它不编
`Tools/main.swift`），然后用旧的 `build/dump` 导 HTML 去验证，看到图片还是靠左，差点认定"改 CSS 没用"。
现在 `build.sh` 里有一段专门编 dump。注意它只能编 `Sources/Core/*.swift`：UI 层有 `@main`，跟
`Tools/main.swift` 的顶层代码冲突（`statements are not allowed at the top level`）。

**不能用 `rm -rf` 清旧产物。** 安全钩子会拦；更坑的是 hook 拦掉之后 `ditto` 会"合并"进旧 bundle
而不是新建，于是产物里混着上一版的文件，看时间戳还以为重建了。现在改成 `mv` 到 `build/old-<ts>`。

**LaunchServices 要主动刷新。** 重新打包后同一个路径的 app，Finder 双击文件可能还是走旧记录（表现成
"双击没反应、只把 App 打开，不打开文件"）。`build.sh` 末尾对 app 跑两遍 `lsregister -f`。

## 图标

图标是代码画的（`Tools/make-icon.swift`，纯 CoreGraphics，没有 Figma/Sketch 源文件），
`./Tools/make-icon.sh` 出 `Resources/AppIcon.icns`，`build.sh` 只负责把它拷进 bundle。

**macOS 26 起会给"四周带透明留白"的旧式图标垫一层灰底板。** 实测 macOS 27：824 见方、
圆角外透明的标准老图标，被系统塞进一个灰色圆角底板里，蓝色缩在中间。所以默认出**满幅不透明**版，
让系统的圆角裁切作用在自己的图形上，看起来才像原生图标。给 macOS 15 及更早出图时用
`ICON_STYLE=squircle`（那代系统不裁切，满幅方块反而比系统图标大一圈）。

**`CGGradient` 默认不延伸到起止点之外。** 斜向渐变（比如左上角到右下角）会让画布两个角压根没被填充，
alpha = 0 —— 于是又变成"带透明留白的图标"，白折腾。必须传
`options: [.drawsBeforeStartLocation, .drawsAfterEndLocation]`。这个坑一开始被误判成"系统加了底板"，
因为导出预览里透明角看着像白色。

**验证系统到底怎么渲染**，别信 PNG 原图：把 `.icns` 塞进一份 app 拷贝（换到 `/tmp/xxx.app` 这种新路径，
否则 LaunchServices 按路径缓存图标），再用 `NSWorkspace.shared.icon(forFile:)` 导 PNG 出来看。

## 解析

**`XMLTok.local` 一律小写。** 所有标签比较必须用小写字符串。踩过一次：样式加载里写了
`"numId"` / `"basedOn"` / `"outlineLvl"`，永远不匹配 —— 症状是 docx 的列表项没有项目符号和编号，
但别的一切正常，很容易以为是编号解析写错了。用正则扫 `(\.open|\.close), "X"` 能一次揪出全部大写写法。

**DrawingML 和 WordprocessingML 的语法不一样。** 这是 PPT 渲染崩过两次的根因：

- Word：格式是**子元素** —— `<w:b/>`、`<w:sz w:val="28"/>`、`<w:jc w:val="center"/>`
- PPT：格式是**属性** —— `<a:rPr sz="2400" b="1"/>`、`<a:pPr algn="l" marL="457200"/>`

按 Word 的写法去读 PPT，症状是"字号全丢、全部退化成默认值、对齐也丢了"。统一在 `case "rpr"` / `case "ppr"`
里一次性把属性读出来。

**`<a:ln>`（边框）不写成 `lin`。** 写错的时候 `inLn` 状态机错乱，把边框色当成了填充色，表现为
"封面红色背景没铺满、底部装饰条错位"。另外 `<a:ln/>` 这种 selfClosing 的要直接 break，不要置 `inLn`。

**`<a:txBody>` 里的 `<a:bodyPr>` 必须由 `renderTextBody` 自己吃掉。** 之前 outer switch 去读它，
永远读不到（因为整个 txBody 被 renderTextBody 消费了），于是 `wrap="none"` 没生效 —— 120pt 的大字
被固定宽度压成两行（"概论""通关"各一行）。正确做法是 `renderTextBody` 里读 `wrap/anchor/lIns/...`，
对 nowrap 的加 `.tx.nowrap{width:max-content; white-space:nowrap}`。

**渐变不能只取第一个色标。** 装饰圆是 `<a:gradFill>` 带 `alpha val="30000"` 的浅黄渐变，只取首色
会渲染成刺眼的实心黄块。要收 `GradStop` 数组 + `alpha`，输出 `linear-gradient` / `radial-gradient`，
并配一个 `rgba()` 辅助。半透明填充同理：胶囊按钮是 `alpha=16000` 的白色叠加，不处理 alpha 就是白底白字。

**图片段落要 `display:inline-block`，不能 `display:block`。** Word 里的内联图片是行内元素，靠段落的
`text-align` 决定居中/靠右。一旦写成 block，`text-align:center` 对它完全无效，所有"居中图片"都会贴到
左边 —— 而且这个 bug 很隐蔽：HTML 里 `style="text-align:center"` 明明是对的，只有对比源文件的
`<w:jc w:val="center"/>` + 量像素位置才能确认。

## 写回

**字节范围替换，不是重新序列化。** 解析时记下每个 `<w:t>` / `<v>` 的**原始字节区间**，编辑时从后往前
`replaceSubrange`，再整包重压。这样才能做到"只有 document.xml 变了，其余 17 个条目逐字节一致"——
`styles.xml` 有 349 KB，重新序列化一遍极容易改坏。

**docx 段落编辑的取舍：** 新文字塞进第一个 `<w:t>`，同段其余 `<w:t>` 清空。这样段落原有的 run 格式
（字体/字号/颜色）保住了，代价是"一段里多种混排"会被压成第一种。注释里写明了是刻意取舍。

**xlsx 不做公式重算。** 显示的是 Excel 上次保存的缓存值，改完保存交给 Excel 重算。这是"查看器"定位下
的正确取舍，不要为了"看起来对"去实现一个半个公式引擎。

## UI

**用 `Window` 不用 `WindowGroup`。** 查看器只需要一个窗口。`WindowGroup` 下每 open 一次文件就多一个窗口，
而所有窗口共享同一个 `Workspace` 单例 —— 后开的文档会把前面窗口的内容一起换掉，看起来像"边栏里的东西串了"。
（诊断时数了窗口数：连续 open 几次就累积了几个窗口。）

**侧边栏的内容容器要绑 `.id(store.sideIdentity)`。** 三个 `ForEach`（大纲/工作表/幻灯片）落在同一个
ViewBuilder 位置上，SwiftUI 按位置复用视图身份，于是幻灯片列表的第一行会显示成上一份 docx 的标题、
并且丢掉自己的序号。只给分支加 `.id("side-ppt")` 不管用，要给整个容器绑到当前文档。同时 `LazyVStack`
换成 `VStack`（最多几十行，不需要懒加载，而 lazy 会缓存旧行）。

**不能用 `@Observable`。** 命令行 `swiftc` 下宏插件报 `ObservableMacro could not be found ... malformed
response`。统一用 `ObservableObject` + `@Published`。

**属性名 `zip` 会被标准库遮蔽。** `value of type '(Sequence1, Sequence2) -> Zip2Sequence<...>' has no
member 'entries'`。三个解析器里的都改名成 `archive`。

## 验证方法

**CLI 导出 + Chrome 截图** 是主力回路，GUI 只负责"解析 + 落盘 + 显示"：

```bash
./build.sh && build/dump 样本.docx /tmp/out.html
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --disable-gpu --no-sandbox --user-data-dir=/tmp/crprof \
  --screenshot=/tmp/out.png --window-size=900,1400 --hide-scrollbars \
  --virtual-time-budget=3000 file:///tmp/out.html
```

注意 `--headless` 单用在这台机器上不出图，要 `--headless=new` 加 `--user-data-dir`。

**判断"居中没居中"要量像素，不能靠眼睛。** 读 PNG 找目标色块的 x 范围和纸张白底的 x 范围，比中心点。
"看起来差不多"曾经放过一个真实的偏移。

**GUI 自动化点击的坐标换算：** `screencapture` 全屏出的是 2940×1912 物理像素，逻辑分辨率 1470×956，
而 Read 显示的是缩放后的 1024 宽 —— 直接拿看到的坐标去点会偏。最稳的做法是用
`screencapture -R x,y,w,h` 精确框住窗口截图，显示坐标 × (w/显示宽) + 偏移 就是逻辑坐标。
另外 `Window` 场景会记住上次窗口位置，每次测试前都要重新定位。

**改完要验，别信"应该没影响"。** 这轮改了 Window/侧边栏/图片 CSS 之后，编辑保存路径还是要重跑一遍
（双击改字 → `⌘S` → 用 python-docx + openpyxl 独立读回，逐条目比 md5）。
